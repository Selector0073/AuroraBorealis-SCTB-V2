# AuroraBorealis SCTB - документація

Вітаємо в документації команди **AuroraBorealis** (Студентське конструкторсько-технологічне бюро, ЛНТУ).

Це головна сторінка. Тут зібрано правила, за якими ми працюємо в репозиторії: як писати документацію, як вносити зміни в код і як відстежувати завдання. Прочитайте її повністю перед своїм першим внеском.

---

## 1. Правила роботи з репозиторієм

### Головне правило

> **Комітити напряму в `main` заборонено.**
> Усі зміни - код, документація, конфіги - потрапляють у `main` лише через Pull Request.

Це стосується всіх учасників команди, зокрема й керівника.

### Порядок роботи

1. Візьміть завдання з дошки в KanbanFlow і перенесіть його в колонку **In progress**.
2. Оновіть локальний `main` і створіть нову гілку від нього:

```bash
    git checkout main
    git pull
    git checkout -b feature-N
```

3. Робіть коміти **тільки в своїй гілці**.
4. Надішліть гілку на GitHub і відкрийте Pull Request у `main`:

```bash
    git push -u origin feature-N
```

5. Дочекайтеся рев'ю.
6. Після схвалення PR зливається в `main`, а гілка видаляється.
7. Перенесіть картку в колонку **Done**.

### Коміти

- Один коміт - одна логічна зміна.
- Бажано використовувати `Conventional Commits`(Якщо хочете можна використовувати `Commitizen`).

### Pull Request

- Перед відкриттям PR переконайтеся, що проєкт збирається, а тести проходять (`make test`).
- Відповідайте на коментарі рев'юера в самому PR і додавайте виправлення новими комітами в ту саму гілку.

## 2. Трекінг завдань у KanbanFlow

Для зручності і щоб декілька людей не робили одну і ту саму роботу - використовуйте `KanbanFlow`. Якщо ви зрозуміли що в проект потрібно щось додати - створіть тікет в табличці `Ready`.

**Дошка команди:** [KanbanFlow](https://kanbanflow.com/board/Lz7yheS).

### Кольори

Тікети діляться на 3 кольори:

- Зелений: не срочне завдання яке можна зробити потім
- Жовтий: Завдання яке бажано зробити швидше/потрібно зробити щоб виконувати зелені завдання
- Червоний: завдання яке ламає сервіс

Коли берете завдання - зважайте на його колір.

### Правила

- Кожне завдання - окрема картка з коротким зрозумілим заголовком.
- В одного завдання один виконавець.
- Статус картки завжди має відповідати реальності. Почали роботу - перенесли в **In progress**, відкрили PR - в **Review**, злили - в **Done**.
- Не беріть у роботу більше завдань, ніж реально встигаєте. Краще мало карток в **In progress**, ніж багато недороблених.
- Винекли проблеми - повідомте команду і попросіть про допомогу.

### Колонки дошки

| Колонка       | Значення                                                |
|---------------|---------------------------------------------------------|
| **To do**     | Завдання сформульоване, але ще ніхто не почав над ним працювати |
| **In progress** | Виконавець працює над завданням, гілка створена       |
| **Review**    | Відкрито PR, очікується рев'ю                           |
| **Done**      | PR злито в `main`, завдання завершено                   |

Назви колонок можна змінити на дошці, але зміст і послідовність мають залишитися такими самими.

## 3. Як писати документацію

Документація лежить у цьому ж репозиторії, у теці `docs/`, і пишеться на **Markdown**. Сайт будується за допомогою [MkDocs](https://www.mkdocs.org).

### Публікація відбувається автоматично

Вручну нічого публікувати **не потрібно**. Після того як ваш PR злито в `main`, документація автоматично збирається й оновлюється на сайті. Тому:

- не комітьте згенеровану теку `site/`;
- не намагайтеся самостійно деплоїти сайт;
- у `main` має потрапляти тільки та документація, яка збирається без помилок.

### Правила оформлення

**Файли та структура**

- Назви файлів: латиницею, малими літерами, слова через дефіс: `getting-started.md`, `api-overview.md`.
- Одна сторінка - одна тема. Якщо сторінка розрослась, розбийте її на кілька.
- Кожна сторінка починається з **одного** заголовка першого рівня (`# Заголовок`). Далі використовуйте `##`, `###` і так далі, не перескакуючи рівні.
- Складні теми групуйте в підтеки: `docs/docs/backend/overview.md`.

**Текст**

- Пишіть коротко і по суті. Документацію читають, щоб швидко знайти відповідь.
- Починайте з того, що це і навіщо, а вже потім переходьте до деталей.

### Що документувати

- Публічні API, формати даних, конфігураційні параметри.
- Очікувані вхідні дані функцій.

Змінили поведінку коду - оновіть документацію **в тому самому PR**. Так вона не застаріває.
